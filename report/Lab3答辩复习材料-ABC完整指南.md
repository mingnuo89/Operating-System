## 一、先用两分钟讲清实验

### 1.1 一句话概括

本实验让内核具备处理 Trap 的基本能力：**发生中断或异常 → 保存现场 → 分发处理 → 恢复现场 → 返回执行流**。

Trap 是 RISC-V 对中断和异常的统称。可以把它想成做作业时突然被打断：你先记住做到哪一页、手里拿着什么，处理临时事情，回来时根据记录接着做。内核中的这份“现场记录”就是 `trapframe`。

### 1.2 三人的工作如何衔接

```text
              CPU 遇到中断或异常
                      ↓
       硬件记录 sepc、scause 等信息，跳到 stvec
                      ↓
成员 A    __alltraps → SAVE_ALL → 构造 trapframe → trap(tf)
                                                ↓
                                 trap_dispatch(tf) 判断类型
                                  ↙                     ↘
成员 B             interrupt_handler(tf)          exception_handler(tf)  成员 C
                     时钟中断、其他中断             非法指令、断点、兜底
                     设置下一次时钟                 必要时更新 tf->epc
                                  ↘                     ↙
                   trap() 返回 → __trapret → RESTORE_ALL → sret
```

注意：`SAVE_ALL` 在框架里已经给出；成员 A 要完成的是与之对应的 `RESTORE_ALL` 和 `__alltraps` 中调用 C 处理函数的部分。

### 1.3 适合开场的口述

> Lab 3 的核心是建立 Trap 处理闭环。发生异常或中断时，硬件先记录原因和返回地址并跳转到预先设置的入口；汇编代码保存寄存器，构造 Trap frame，把它传给 C 语言的 trap 函数。C 层根据原因分发：时钟中断需要设置下一次时钟事件并累计 ticks；非法指令和断点需要输出信息并按指令长度调整返回地址。最后汇编恢复上下文，通过 sret 返回。我负责的是异常处理及相关验证。

## 二、基础概念：先把名词讲准

### 2.1 中断、异常、Trap 有什么区别？

| 概念 | 触发来源 | 与当前指令的关系 | 实验例子 |
|------|----------|-----------------|----------|
| 中断 interrupt | 时钟或外设等事件 | 异步，通常不由当前指令直接产生 | S 模式时钟中断 |
| 异常 exception | 执行指令时产生的事件 | 同步，与当前指令有关 | 非法指令、断点 |
| Trap | RISC-V 对上述控制转移事件的统称 | 可以是中断，也可以是异常 | 本实验的统一入口 |

“异步”不是说发生时间完全随机，而是说事件不由当前这条指令本身产生。`ebreak` 是主动执行的指令，所以引发的是同步异常。

### 2.2 为什么要保存现场？

中断处理程序也需要用寄存器，例如计算、调用函数、输出文字。如果直接覆盖了被打断代码的寄存器，返回后原程序就可能拿到错误的数据。仅保存 PC 不够：寄存器、栈指针和部分状态寄存器都可能影响后续执行。

### 2.3 M、S、U 三种特权级

- **M 模式**：机器模式，权限最高；课程环境中 OpenSBI 固件在这一层提供底层服务。
- **S 模式**：监管模式，本实验中的 ucore 内核运行于此。
- **U 模式**：用户模式，普通应用程序运行于此，权限较低。

硬件和固件可以将一部分 Trap 委托给 S 模式处理。不要说“所有 Trap 一定从用户态进入内核”：实验当前运行的是内核，Trap 也可以从 S 模式进入 S 模式处理。

### 2.4 硬件做什么，软件做什么？

当一个被委托到 S 模式的 Trap 被接收时，硬件负责设置 `sepc`、`scause`、相关的状态位以及必要的异常附加信息，并根据 `stvec` 跳转。硬件不会替内核把全部通用寄存器整理成 C 结构体；这一步由 `SAVE_ALL` 等软件代码完成。

`sepc` 对同步异常一般指向发生异常的指令；对中断则记录恢复时应继续执行的位置。软件要依据事件性质决定是否修改它，不能对所有 Trap 都统一加 4。

### 2.5 核心 CSR 速查

| 寄存器 | 作用 | 对应的 frame 字段/用法 |
|--------|------|------------------------|
| `stvec` | S 模式 Trap 入口及模式 | `idt_init()` 写入 `__alltraps` |
| `sepc` | Trap 返回时使用的指令地址 | 保存为 `tf->epc` |
| `scause` | 记录 Trap 原因；最高位区分中断和异常 | 保存为 `tf->cause` |
| `sstatus` | 保存特权级、中断使能等状态 | 保存为 `tf->status` |
| `stval` / 框架中的 `sbadaddr` 名称 | 异常附加信息，例如某些异常的出错地址 | 保存为 `tf->badvaddr` |
| `sscratch` | 给 S 模式软件使用的临时 CSR | 此框架入口用来暂存原始 `sp` |
| `sie` | 按来源控制 S 模式中断使能 | `clock_init()` 使能时钟中断来源 |

CSR 是控制与状态寄存器；通用寄存器用来参与普通计算，CSR 则承载体系结构控制信息。

### 2.6 `sstatus` 中与 Trap 有关的位

- `SIE`：当前处于 S 模式时，控制 S 模式全局中断使能。
- `SPIE`：保存进入 Trap 前的 SIE 状态，供返回时恢复。
- `SPP`：记录陷入 S 模式前的特权级，决定 `sret` 返回 U 模式还是 S 模式。

因此，`sret` 不一定返回用户态。在本实验的内核态测试中，也可能返回 S 模式的内核代码。

### 3.2 `kern_init()` 的顺序

框架初始化控制台与内存等环境，调用 `idt_init()` 设置入口，随后初始化时钟并通过 `intr_enable()` 打开全局中断。源码中 `idt_init()` 出现两次，讲解时可以说明这是当前框架的实际写法，关键效果是把 `stvec` 指向 Trap 入口。

`clock_init()` 先使能时钟中断来源、安排首个时钟事件并初始化 `ticks`；`intr_enable()` 再设置 `sstatus.SIE`。这样中断到来时内核已有入口和处理环境。

### 3.3 `idt_init()` 做了什么？

```c
extern void __alltraps(void);
write_csr(sscratch, 0);
write_csr(stvec, &__alltraps);
```

- `extern` 表示该符号在其他文件定义，此处告诉 C 编译器它存在。
- 写 `sscratch` 为 0：初始化框架使用的暂存 CSR。
- 把 `__alltraps` 地址写进 `stvec`：设置 S 模式统一入口。入口 4 字节对齐，低位模式为 Direct。

不要把 `idt_init` 的名字误认为它创建了 x86 的完整 IDT；这里实际做的是设置 RISC-V 的 Trap 入口。

## 四、成员 A：Trap frame、保存、调用与恢复

### 4.1 `trapframe` 是什么？

`trapframe` 是存放被打断执行流状态的结构体。简化看：

```c
struct trapframe {
    struct pushregs gpr;  // x0 到 x31 的保存位置
    uintptr_t status;     // sstatus
    uintptr_t epc;        // sepc
    uintptr_t badvaddr;   // 附加信息
    uintptr_t cause;      // scause
};
```

`uintptr_t` 可以保存地址宽度的数据。RV64 每项 8 字节，共 32 个通用寄存器位置加 4 个 CSR 位置，即 36 × 8 = **288 字节**。真实内存偏移必须与汇编保存位置一致。

| 内容 | 相对 frame 的槽位 | RV64 字节偏移 |
|------|------------------|---------------|
| `x0` | 0 | 0 |
| `x1` / `ra` | 1 | 8 |
| 原来的 `x2` / `sp` | 2 | 16 |
| `x31` | 31 | 248 |
| `status` | 32 | 256 |
| `epc` | 33 | 264 |
| `badvaddr` | 34 | 272 |
| `cause` | 35 | 280 |

`x0` 总是零，虽然 frame 中保留对应槽位，但恢复时不能通过写 `x0` 改变它。

### 4.2 `SAVE_ALL` 逐步解释

```asm
csrw sscratch, sp
addi sp, sp, -36 * REGBYTES
STORE x1, 1*REGBYTES(sp)
# 其余通用寄存器也按对应槽位保存
csrrw s0, sscratch, x0
csrr s1, sstatus
csrr s2, sepc
csrr s3, sbadaddr
csrr s4, scause
STORE s0, 2*REGBYTES(sp)
STORE s1, 32*REGBYTES(sp)
STORE s2, 33*REGBYTES(sp)
STORE s3, 34*REGBYTES(sp)
STORE s4, 35*REGBYTES(sp)
```

1. `csrw sscratch, sp` 暂存进入 Trap 时的旧栈顶。
2. `addi` 让栈向低地址扩展 36 个槽位，新 `sp` 指向 frame 起始位置。
3. `STORE` 根据寄存器编号写入对应的槽位；寄存器保存顺序可从代码核对。
4. `csrrw s0, sscratch, x0` 同时读取 `sscratch` 旧值到 `s0`，并把零写入 `sscratch`；这时 `s0` 里的值是原 `sp`。原本的 `s0` 已在前面存过，所以可以拿来做临时寄存器。
5. `csrr` 把 CSR 读入通用寄存器，再由 `STORE` 写进 frame。CSR 不能直接作为普通内存存储指令的数据来源。

**为什么 `sp` 特殊？** `addi` 后的 `sp` 已经指向新 frame；如果直接把此时的 `sp` 当成原始 `sp` 保存，返回后栈的位置就错了。原始值必须先暂存，再放入第 2 号槽位。

### 4.3 `__alltraps` 应该建立什么关系？

它需要先保存现场，再把 frame 指针传给 `trap(struct trapframe *tf)`。按 RISC-V 调用约定，第一个参数放在 `a0`，因此典型思路是把当前 `sp` 送入 `a0`，调用 `trap`，返回后进入 `__trapret`。

理解要点：调用前现场已经保存到栈内存，因此 C 函数可以使用普通寄存器；但 `sp` 指向的 frame 必须保持正确，调用返回后才能继续恢复。实际汇编要以组员最终实现为准。

### 4.4 `RESTORE_ALL` 的要求和顺序

`RESTORE_ALL` 要与 `SAVE_ALL` 的槽位**逐一对应**。从 frame 恢复返回需要的 CSR，特别是 C 函数可能修改过的 `epc`；再恢复通用寄存器，最后恢复旧的 `sp`，然后执行 `sret`。

为什么通常最后恢复 `sp`？因为当前 `sp` 是访问 frame 的基地址。如果提前用旧 `sp` 覆盖它，后续 `LOAD ... offset(sp)` 会从错误的位置读取。恢复过程中用来暂存 CSR 的寄存器，也必须在使用完成后恢复其原值。

`badvaddr`、`cause` 是事件信息，本实验返回路径关注 `sstatus`、`sepc` 和通用寄存器；不要说所有 CSR 都必须写回才能返回。

### 4.5 A 部分的汇编阅读示例

下面是为了理解数据流写的**示意片段**，省略了大量寄存器，不是可直接提交的完整 `RESTORE_ALL`：

```asm
__alltraps:
    SAVE_ALL             # 原寄存器已被保存；sp 指向 frame
    mv   a0, sp          # 第一个 C 参数是 frame 的地址
    jal  trap            # 调用 C 的 trap(tf)
                         # 返回后继续 __trapret
__trapret:
    RESTORE_ALL
    sret
```

如果把 `RESTORE_ALL` 展开，核心思路是：

```asm
    LOAD t0, 32*REGBYTES(sp)  # 取 status
    csrw sstatus, t0
    LOAD t0, 33*REGBYTES(sp)  # 取可能被 C 修改过的 epc
    csrw sepc, t0
    # 按原槽位恢复 x1、x3 ... x31；包括最终恢复 t0
    # 必须在所有依赖当前 sp 的 LOAD 后，再恢复 x2/sp
    LOAD sp, 2*REGBYTES(sp)
```

`jal trap` 会将返回位置写入 `ra`，但原 `ra` 已经在 `SAVE_ALL` 中保存；C 函数返回后统一恢复。完整版本还要恢复所有需要恢复的寄存器，并与项目中宏定义的 `LOAD`、`REGBYTES` 对应。

### 4.6 `sret` 具体完成什么？

它是从 S 模式 Trap 处理返回的特权指令：按 `sepc` 设置后续 PC，并按 `sstatus` 的相关状态恢复特权级和中断使能。若 C 层只是修改了 `tf->epc`，但恢复代码没有将这个值写回 `sepc`，`sret` 看不到这次修改，异常可能再次发生。

### 4.7 A 部分自测问题

1. **为什么用汇编？** 入口必须在普通 C 函数使用寄存器和栈之前保存被打断现场，还需要操作 CSR 和执行 `sret`。
2. **只保存被调用者保存寄存器够吗？** 不够。Trap 可以打断任意位置，不是普通函数调用，不能假设调用者已经按函数调用约定保存其临时寄存器。
3. **`a0` 原值会不会丢？** 先由 `SAVE_ALL` 存入 frame，之后才用 `a0` 传参，最终恢复。
4. **`ra` 为什么保存？** Trap 可能打断正在使用 `ra` 的代码，而调用 `trap()` 本身也会改变返回地址寄存器。
5. **为什么 `SAVE_ALL` 和 `trapframe` 布局必须一致？** C 层按结构体偏移读写数据，汇编按固定偏移存取；不一致会把某一寄存器误当成另一字段。
6. **`sscratch` 在本框架中是不是自动完成用户栈切换？** 不是。当前给出的 `SAVE_ALL` 直接暂存 `sp`；不要将指导书中一般性用户态方案说成这个框架已经实现的功能。

## 五、成员 B：中断分发与时钟

### 5.1 `trap()` 怎样判断中断或异常？

当前框架的 `trap_dispatch()` 核心是：

```c
if ((intptr_t)tf->cause < 0) {
    interrupt_handler(tf);
} else {
    exception_handler(tf);
}
```

RISC-V 的 `scause` 最高位标记中断。RV64 环境下将这一位为 1 的值按 `intptr_t` 有符号数理解，结果为负，因此进入中断分支；最高位为 0 则进入异常分支。

区分中断后，还要取得其余位表示的原因编号；处理具体 `IRQ_S_TIMER` 等类型时不能把带最高中断标志的整个数直接当成普通编号比较。具体去标志的实现要与最终代码一致。

### 5.2 `interrupt_handler()` 要完成什么？

根据指导书，时钟中断分支应安排下一次事件、让 `ticks` 每次加一，达到 `TICK_NUM` 的整数倍时输出统计信息，并在规定输出次数后调用框架提供的关机接口。其他已识别中断输出对应提示；未知类型调用 `print_trapframe(tf)` 辅助诊断。

这里写的是**功能要求**。当前官方骨架只有 `TICK_NUM` 和 `print_ticks()`，组员实现时还需按框架接口补齐统计和关机逻辑，不要把截图里的测试替身视作最终实现。

### 5.3 B 部分的代码阅读示例

下列代码是依据指导书写的**流程伪代码**，用于解释分支，并非成员 B 的正式实现；具体常量、输出格式与关机接口以组员代码和框架为准。

```c
void interrupt_handler(struct trapframe *tf) {
    uintptr_t number = 去掉最高位中断标志(tf->cause);
    switch (number) {
    case IRQ_S_TIMER:
        clock_set_next_event();       // 安排下一个时钟事件
        ticks++;                      // 本次时钟事件计数一次
        if (ticks % TICK_NUM == 0) {  // 达到输出条件
            print_ticks();
            输出次数++;
            if (输出次数达到规定值) {
                调用框架的关机接口;
            }
        }
        break;
    // 其他已识别中断：输出对应提示
    default:
        print_trapframe(tf);          // 记录未识别的原因与现场
        break;
    }
}
```

思路是先取得去掉标志位的来源编号，再针对时钟中断安排后续事件、计数和检查输出/关机条件。`ticks` 每次中断增长，输出次数只在满足 `ticks % TICK_NUM == 0` 时增长；二者不能混为一谈。

### 5.4 从第一次事件到周期性中断

```text
clock_init()
  ├─ 使能 sie 中的时钟中断来源
  ├─ clock_set_next_event() → sbi_set_timer(当前 time + timebase)
  └─ ticks = 0

intr_enable() 开启全局 S 中断
     ↓ 时间到
Trap → interrupt_handler() → 重新设置下一次事件 → ticks++ → 按条件输出
     ↓
恢复现场 → sret → 继续原执行流
```

`clock_set_next_event()` 安排的是**下一次**事件，并不是调用一次就自动永久周期触发。如果处理时忘记重新安排，后续不会按预期持续触发。

### 5.5 `rdtime`、`timebase` 与 `ticks`

- `rdtime` 读取时间计数；代码中的 `get_cycles()` 在 RV64 下用它取值。这里的 time 计数不要简单等同于 CPU 执行的指令数。
- `timebase = 100000` 是设置下一事件时加的时间计数间隔。按指导书 QEMU 的 10 MHz 时间基准，100000 / 10000000 = **0.01 秒**，即约 10 ms。
- 约每秒 100 次，`TICK_NUM = 100`，因此理想情况下每约 1 秒可输出一次 `100 ticks`。实际输出间隔会受到模拟与执行开销影响，不要声称绝对精确。
- `ticks` 是软件记录的已处理时钟中断次数，不是 `rdtime` 硬件计数值，也不是输出次数。

### 5.6 为什么 `ticks` 是 `volatile`？

它会在中断处理路径中变化，而其他代码可能反复读取。`volatile` 让编译器保留需要的内存访问，避免把值一直当成未变化的寄存器副本。`volatile` 本身不等同于锁，也不保证多核操作原子性。

### 5.7 B 部分自测问题

1. **为什么既有 `sie` 又有 `sstatus.SIE`？** 前者按来源控制，后者是在 S 模式下的全局使能；能否接收具体中断还受其他条件影响。
2. **为什么刚初始化时要设置第一个事件？** 只有先安排事件，系统才会接收到首次时钟中断，后续才有机会继续安排。
3. **处理时为什么还要安排下一次？** SBI 设置的是一个未来时刻的事件；每次处理都要更新下一次目标时刻。
4. **100 ticks 就一定关机吗？** 不一定。100 次中断达到一次输出条件；何时关机还要看要求的输出次数。
5. **时钟中断的 `epc` 一般要加 4 吗？** 不应机械加 4。中断要返回被打断的执行流，框架只在指定异常中为跳过异常指令调整地址。
6. **`sbi_set_timer()` 和 `rdtime` 分别做什么？** 前者向 SBI 请求设置未来的时钟事件，后者读取当前时间计数。

## 六、成员 C：异常处理逐行讲解

### 6.1 当前代码

```c
void exception_handler(struct trapframe *tf) {
    switch (tf->cause) {
    case CAUSE_ILLEGAL_INSTRUCTION:
        cprintf("Illegal instruction at 0x%lx\n", tf->epc);
        break;
    case CAUSE_BREAKPOINT:
        cprintf("Breakpoint at 0x%lx\n", tf->epc);
        break;
    default:
        print_trapframe(tf);
        return;
    }

    uint16_t instruction = *(const uint16_t *)tf->epc;
    tf->epc += (instruction & 3) == 3 ? 4 : 2;
}
```

这段代码是工作区中实际存在的实现。它只面向本实验约定：异常指令地址可由内核读取，目标测试涉及 16 位或 32 位指令。

### 6.2 参数和类型分发

`struct trapframe *tf` 是 frame 的地址。`tf->cause` 相当于 `(*tf).cause`，读取硬件异常原因经汇编保存到 frame 后的值。

`switch` 对比已有常量：非法指令异常对应 `CAUSE_ILLEGAL_INSTRUCTION`；断点异常对应 `CAUSE_BREAKPOINT`。两个分支分别输出异常类型和原 `epc`。`break` 只结束 `switch`，所以这两类异常会继续执行下面的地址调整。

`default` 调用 `print_trapframe(tf)`，然后 `return` 结束函数。这样未指定异常会显示诊断信息，也不会落到下面去读取未知地址或修改 `epc`。这只是诊断兜底，不等于修复了其他异常；如果统一返回路径继续回到同一条会重复出错的指令，异常仍可能再次出现。

### 6.3 为什么需要修改 `epc`？

假设非法指令位于 `0x1000`，其长度为 4 字节。如果处理后 `sepc` 仍然指向 `0x1000`，`sret` 会重新执行同一条非法指令，可能反复异常。本实验要求跳过它，所以 C 层将 frame 中的 `epc` 改为 `0x1004`；恢复代码再把它写回 `sepc`。

断点同理：本实验的测试希望处理后继续执行下一条指令。真实系统对异常是否应该跳过取决于具体处理策略；不能推广成“遇到任何异常都跳过”。

### 6.4 为什么读取 16 位？

```c
uint16_t instruction = *(const uint16_t *)tf->epc;
```

从右向左理解：

1. `tf->epc` 是整数形式保存的异常指令地址。
2. `(const uint16_t *)` 把它解释为指向 16 位只读数据的指针。
3. 前面的 `*` 从这个地址读取一个 16 位半字。
4. 将结果保存到 `instruction`，用于检查最低两位。

这里的 `const` 表示通过这个指针只读取，不写入指令。它并不证明地址一定合法。直接解引用依赖本实验的内核可访问地址前提；如果直接访问不可读地址，处理函数本身可能再次发生异常。

### 6.5 如何判断 2 字节还是 4 字节？

```c
tf->epc += (instruction & 3) == 3 ? 4 : 2;
```

`3` 的二进制低两位是 `11`。`instruction & 3` 只保留低两位：

| 指令首半字示例 | 低两位 | 本实验判断 | 地址增量 |
|----------------|--------|------------|----------|
| `0x0000` | `00` | 16 位编码 | 2 字节 |
| `0x9002` | `10` | 16 位编码 | 2 字节 |
| `0x007b` | `11` | 32 位编码 | 4 字节 |
| `0x0073` | `11` | 32 位编码 | 4 字节 |

条件表达式 `条件 ? A : B` 表示条件成立选 A，否则选 B；`+=` 把选中的长度加到旧 `epc`。注意这里的步长单位是**字节**，16 位 = 2 字节，32 位 = 4 字节。

这个判断足以区分本实验测试的 16 位和 32 位情况；低两位为 `11` 并不意味着所有可能的 RISC-V 长指令都只有 32 位，本代码没有实现 48 位及以上指令长度解析。

### 6.6 算一遍

假设 `tf->epc = 0x1000`，在该地址读取的低半字是 `0x9002`：

```text
0x9002 & 3 = 2，不等于 3
步长 = 2
新 epc = 0x1000 + 2 = 0x1002
```

如果首半字是 `0x007b`：

```text
0x007b & 3 = 3
步长 = 4
新 epc = 0x1000 + 4 = 0x1004
```

### 6.7 与 A、B 怎么协作？

- 与 A：A 的保存代码把 `sepc` 存到 `tf->epc`，C 在内存里改它，A 的恢复代码再写回 `sepc`，`sret` 才会跳到新地址。
- 与 B：C 处理同步异常，B 处理中断；两者由 `trap_dispatch()` 根据 `cause` 最高位分发，不能把“跳过异常指令”的操作统一用于时钟中断。
- 未知异常打印 frame 只是提供线索；不修改 `epc` 的后果要据具体异常判断。

### 6.8 C 部分自测问题

1. **为什么不是固定加 4？** 因为实验平台支持压缩指令，部分指令是 2 字节；加错会跳过额外数据或从指令中间继续执行。
2. **为什么不是固定加 2？** 对 4 字节指令只加 2 会落在其后半部分。
3. **为什么不直接修改 `sepc`？** 统一流程以 frame 保存状态；修改 frame，再由恢复代码写回，保持 C 层与汇编接口一致。
4. **`break` 和 `return` 区别是什么？** `break` 退出 `switch`，继续执行函数后面的地址更新；`return` 直接退出函数。
5. **非法指令和断点的输出地址是更新前还是更新后？** 当前代码先输出，再增加 `epc`，所以输出的是异常发生地址。
6. **`instruction & 3` 是什么？** 取读取到的半字最低两位，其他位清零。
7. **`uint16_t` 的 16 是字节数吗？** 不是，是位数，16 位等于 2 字节。
8. **其他异常 `epc` 为什么不动？** 题目要求以打印 frame 兜底，不能在不知道异常类型和恢复策略时随意跳过指令。
9. **`tf->epc` 是原始 CSR 本身吗？** 不是，它是 CSR 内容在内存中的保存副本，需要后续恢复到 `sepc`。
10. **`stval` 一定是非法指令本身吗？** 不一定。它是异常附加信息，不同异常含义不同；本实现通过 `epc` 读取内核可访问指令半字。

## 七、关闭中断与原子性

指导书用物理页分配举例：内核修改空闲链表等共享数据时，如果被本地中断处理打断，处理路径又访问同一数据，可能看到不一致的中间状态。框架用 `local_intr_save(flag)` 保存原来的中断状态并关闭中断，操作结束后通过 `local_intr_restore(flag)` 恢复。

为什么不能无条件开启中断？进入临界区之前，中断可能已经处于关闭状态；如果离开时无条件开启，就改变了调用者原有状态。保存旧值再恢复，能正确处理这种嵌套关系。

`do { ... } while (0)` 常用于多语句宏，让它在 `if/else` 等位置表现得像一条语句。关闭本地中断只约束本地处理器上的中断执行，不等于解决多核并发的所有问题；`volatile` 也不是互斥锁。

## 九、高频追问：按老师提问的顺序练习

### 基础流程

**1. 为什么计算机需要中断？** 让处理器在等待设备或时间事件时不必一直轮询，并能及时响应需要处理的事件。

**2. 中断与异常分别举例？** 时钟事件是中断；执行非法指令和 `ebreak` 是异常。

**3. Trap 一定从 U 态到 S 态吗？** 不一定。已委托给 S 模式的 Trap 也可能在 S 模式内核运行时发生并由 S 模式处理。

**4. 硬件负责保存所有寄存器吗？** 不负责。硬件记录关键 CSR 和状态，通用寄存器由入口软件保存。

**5. 一次 Trap 的控制流是什么？** 硬件记录 → `stvec` 指向入口 → 保存 frame → C 分发并处理 → 恢复 frame → `sret`。

**6. 什么是上下文？** 为使被打断执行流恢复所需的状态，例如通用寄存器、栈指针、返回地址和状态位。

### 成员 A

**7. `stvec` 的作用？** 保存 S 模式 Trap 入口地址及模式；本实验采用统一入口。

**8. `__alltraps` 与 `trap()` 的关系？** 前者是汇编入口，完成保存及传参；后者是 C 层统一处理入口。

**9. `a0` 在调用中做什么？** 根据调用约定传递第一个参数，即当前 frame 地址。

**10. 为什么 `sp` 要特别保存？** 为 frame 分配栈空间会先修改 `sp`，必须保存修改前的原值。

**11. frame 为什么是 288 字节？** RV64 中 32 个通用寄存器槽位和 4 个 CSR 槽位，每项 8 字节。

**12. `sscratch` 在当前 `SAVE_ALL` 中做什么？** 临时保存原 `sp`，随后读取它并清零该 CSR。

**13. 为什么最后恢复 `sp`？** 恢复其他字段时还需要当前 `sp` 指向 frame。

**14. 为什么要恢复 `sepc`？** `sret` 根据它确定返回地址，C 层可能已经通过 `tf->epc` 修改了该地址。

**15. `sret` 一定切回 U 态吗？** 不一定，由保存的 `sstatus.SPP` 决定。

**16. 为什么保存 `ra` 和临时寄存器？** 被打断的代码可能正在使用它们，而处理函数和普通调用会覆盖它们。

### 成员 B

**17. 如何从 `cause` 区分中断和异常？** 查看最高位；框架通过转成有符号整数后判断负数来分支。

**18. 中断标志位和具体原因码有什么区别？** 最高位表示中断，其他位表示具体来源；分类后应去掉标志位再判断编号。

**19. 为什么第一次要设置时钟事件？** 否则没有首个定时事件，就无法进入后续周期处理。

**20. 为什么每次处理都要设置下一次事件？** 当前 SBI 定时接口安排下一次触发，而不是永久重复事件。

**21. `ticks` 与 `timebase` 区别？** 前者是已处理中断次数，后者是设置下次事件时所加的时间计数间隔。

**22. 为什么需要 `volatile`？** 告诉编译器该值可能在普通控制流之外变化；它不是同步原语。

**23. 时钟中断为什么通常不跳过当前指令？** 它不是由当前指令出错触发，应按保存的继续位置恢复执行。

**24. 100 次中断和一次输出是什么关系？** 在 `TICK_NUM = 100` 的要求下，每达到其整数倍输出一次；关机还要看累计输出次数要求。

### 成员 C

**25. `tf->cause` 从哪来？** CPU 写 `scause`，汇编入口读取并保存在 frame 中。

**26. 非法指令和断点为什么要调整 `epc`？** 本实验要跳过触发异常的指令，避免返回后重复执行。

**27. `epc += 4` 有什么问题？** 压缩指令可能只有 2 字节，固定加 4 会越过下一条指令。

**28. 怎样看指令长度？** 当前实验中取指令首半字最低两位，非 `11` 为 2 字节；为 `11` 按本实验 32 位测试处理。

**29. `uint16_t` 为什么足够用于判断？** 判断只需要首半字的最低两位，不必读取整条 32 位指令。

**30. 为什么默认分支先打印再返回？** 未指定异常需要诊断信息，不能默认读异常地址并跳过它。

**31. 未知异常打印后一定解决了吗？** 没有。其原因仍可能存在，直接返回可能重复陷入。

**32. 直接读取 `epc` 指向的内存有什么前提？** 地址对于当前处理代码可安全读取；这属于本实验内核测试前提。

**33. `epc` 和 `sepc` 区别？** 前者是 frame 中的字段，后者是 CPU CSR；恢复代码把 frame 的值写回 CSR。

**34. `break` 和 `return` 在这段代码中各有什么作用？** `break` 退出 `switch` 后继续更新地址；`return` 结束函数，避免默认异常进入更新代码。

**35. 断点异常是中断吗？** 不是，`ebreak` 由当前指令同步触发，属于异常。

### 测试与设计

**36. 单元测试通过是否证明 `sret` 正确？** 不能。单元测试只直接调用 C 函数，需要 QEMU 整合测试覆盖实际 Trap 入口和返回。

**37. 为什么需要测试 16 位、32 位两种情况？** 检验两种地址增量，避免只对其中一种指令长度正确。

**38. 为什么要测试未知异常？** 确认能调用兜底输出，且不会读取无效指令地址或误改 `epc`。

**39. 为什么不能拿临时替身的评分当成小组最终成绩？** 入口和时钟处理不是正式队友代码，组合不同，必须重新整合验证。

**40. 把 `epc` 写回去之前恢复所有寄存器有什么风险？** 如果还需要借助某个通用寄存器写 CSR，可能破坏刚恢复的值；恢复顺序必须保证最终状态正确。

**41. 保存中断状态后为什么不直接在退出临界区时总是开中断？** 原来可能已关闭；应该恢复原状态。

**42. `print_trapframe()` 的价值是什么？** 输出寄存器、状态、异常地址和原因，为分析未处理异常提供现场信息。
