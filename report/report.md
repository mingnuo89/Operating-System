## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本章实验主要围绕 RISC-V 操作系统的中断与异常处理机制展开。在前两个实验中，我们已经完成了最小内核的启动和基本的内存管理功能，但此时内核还缺少对中断和异常的完整处理能力。因此，本章需要在已有内核的基础上，实现 Trap 的上下文保存与恢复、中断和异常的分类处理，以及时钟中断等功能。

整个实验的核心是建立一套完整的 Trap 处理流程。当 CPU 发生中断或异常时，首先由硬件记录相关状态，并跳转到指定的 Trap 入口；然后通过汇编代码保存当前执行环境，进入 C 语言处理函数，根据 Trap 类型执行对应的操作；最后恢复原来的寄存器状态，通过 sret 返回被中断的执行流。

通过这一过程，操作系统就能够在不破坏原有执行状态的情况下处理中断和异常，为后续实现进程调度、系统调用等功能提供基础。

### 3.2 功能的逐步实现

本章实验按照“Trap 上下文管理 → Trap 入口与返回 → 中断和异常处理 → 功能测试”的顺序完成，各部分之间存在一定的依赖关系。

1. Trap 上下文的保存与恢复

首先，需要建立完整的上下文管理机制。实验框架已经提供了 SAVE_ALL 宏，可以将 Trap 发生时的通用寄存器和相关 CSR 保存到栈上的 TrapFrame 中。我们需要在此基础上实现 RESTORE_ALL，根据已有的保存布局恢复寄存器状态，并正确处理栈指针 sp。

之所以先完成这部分，是因为无论发生中断还是异常，都需要保证处理完成后能够恢复原来的执行环境，这是整个 Trap 处理流程正常运行的基础。

2. Trap 入口与返回功能

接着，完善 __alltraps 入口，使系统能够在保存上下文后，将 TrapFrame 的地址按照 RISC-V 函数调用约定传递给 C 语言的 trap() 函数。处理完成后，再通过 __trapret 执行 RESTORE_ALL 和 sret，返回原来的执行流。

这一步主要解决汇编代码与 C 语言处理函数之间的衔接问题，使 Trap 处理能够形成完整的进入和返回流程。

3. 中断与异常的分类处理

在完成底层 Trap 处理框架后，进一步实现 interrupt_handler() 和 exception_handler()。

其中，interrupt_handler() 主要负责处理中断，重点是时钟中断。每次发生时钟中断时，需要更新计数器、设置下一次时钟事件，并在达到规定条件时输出统计信息和执行关机操作。

exception_handler() 主要负责处理非法指令异常和断点异常，根据异常原因输出相应信息，并正确调整 tf->epc，避免处理完成后重复执行触发异常的指令。

这一步使内核不仅能够进入 Trap 处理程序，还能够根据不同的中断和异常类型执行对应的处理逻辑。

4. 整体功能测试与验证

最后，将各部分代码整合并进行编译运行，重点检查 Trap 入口和返回流程是否正常、寄存器状态是否能够正确恢复、时钟中断是否能够持续触发，以及非法指令和断点异常能否得到正确处理。

通过这些测试，验证各个模块之间能否正常配合，确保内核具备基本的中断与异常处理能力，为后续实验打下基础。

## 四、实验内容与实现

### 功能模块一：Trap 上下文恢复与 Trap 入口（练习一）

**负责人：** 2410878-吕明诺

#### 模块功能描述

**需要实现/修改的符号（`kern/trap/trapentry.S`）：**

```asm
    .macro RESTORE_ALL      # 从 TrapFrame 恢复处理器状态，与 SAVE_ALL 严格对称
        ...
    .endm

    .globl __alltraps       # Trap 入口点（stvec 指向这里）
__alltraps:
        SAVE_ALL
        ...                 # 把 TrapFrame 基址按调用约定传给 trap()
```

**功能说明：**

本模块负责 Trap 从"进入内核"到"返回原执行流"之间最底层的上下文管理，是整个实验的"地基"：上面的 `interrupt_handler`/`exception_handler` 写得再对，只要上下文恢复错一个寄存器，系统也无法正常运行。

（1）**数据布局：TrapFrame 的 36 个槽位。** `struct trapframe` 由 `struct pushregs`（32 个 `uintptr_t`，依次对应 `x0~x31`）和 4 个 CSR 字段组成，在 RV64 下每个 `uintptr_t` 占 8 字节（`REGBYTES`），所以总大小是 `36 * 8 = 288` 字节：


（2）**`RESTORE_ALL` 要做什么。** 它是 `SAVE_ALL` 的逆操作，但不是简单的"每条 `STORE` 反过来写一条 `LOAD`"，因为有两类东西要特殊对待：**CSR 不能直接从内存写**（RISC-V 只能"通用寄存器 ↔ CSR"），所以必须先用临时寄存器把 `32~35` 槽的值读出来再 `csrw` 回 CSR；**`x2`（sp）不能随手恢复**，因为整个恢复过程都要用 sp 作为基址去寻址，sp 一动，后面所有偏移全错。

（3）**`__alltraps` 要做什么。** 它是 `stvec` 指向的唯一入口（Direct 模式，所有中断与异常都跳到这里）。它做三件事：`SAVE_ALL` 保存现场；把此时 sp 指向的地址作为 `struct trapframe *` 按 RISC-V 调用约定放进 `a0`，调用 `trap()`；`trap()` 返回后落到 `__trapret`，执行 `RESTORE_ALL` 与 `sret`。`jal trap` 会覆盖 `ra`，但 `ra` 已经在 `SAVE_ALL` 里存进 1 号槽，`RESTORE_ALL` 会把它恢复回来，所以不冲突。

（4）**与其它模块的交互。** 向下依赖硬件写好的 `sepc/scause/stval` 与 `sstatus` 的 `SPP/SPIE` 语义；向上供 `kern/trap/trap.c` 中的 `trap()` 使用——`trap()` 只做分发，它可能修改 `tf->epc`（异常处理后要跳过出错指令），所以 `sepc` 的写回必须发生在 `trap()` **返回之后**，否则修改会丢。

（5）**一个必须说清的语义前提。** 本实验 `SAVE_ALL` 第一句就执行 `csrw sscratch, sp`，把陷入前的 sp 写进 `sscratch`，随后 `csrrw s0, sscratch, x0` 把它取出来存到 2 号槽并把 `sscratch` 清 0。因此 **2 号槽里存的是陷入前的 sp，不是 0**。这一点决定了 `x2` 有两种等价恢复方式。

### 功能模块二：异常处理与返回地址调整

**负责人：** 2410849-张祖浩

#### 模块功能描述

**需要实现的函数：**

```c
/* kern/trap/trap.c */
void exception_handler(struct trapframe *tf);
```

**功能说明：**

函数依据 `tf->cause` 处理 `CAUSE_ILLEGAL_INSTRUCTION` 和 `CAUSE_BREAKPOINT`，输出异常地址并跳过引发异常的指令。其他异常调用 `print_trapframe(tf)`；函数本身不负责恢复寄存器，而是将调整后的 frame 交给统一返回流程。

**Spec：**

- 两类指定异常分别输出 `Illegal instruction at`、`Breakpoint at` 和异常地址。
- 读取 `tf->epc` 指向指令的前 16 位，低两位不为 `11` 时按 2 字节更新 `epc`，否则按 4 字节更新。
- 其他异常输出 trapframe，保持 `epc` 原值，不解引用该地址。
- 保持接口及既有函数不变；本实验测试前提是异常指令位于内核可读取地址，指令长度为 16 或 32 位。

#### 异常处理与返回流程

异常发生后，处理器将异常原因和指令位置分别保存在 `scause`、`sepc` 中。入口汇编保存这些寄存器，形成 `struct trapframe`，再将其地址传给 `trap()`。`trap_dispatch()` 根据 `cause` 的最高位将中断和异常分开；对于异常，将同一个 `tf` 交给 `exception_handler()`。因此，这个函数中的 `tf->epc` 是返回地址在内存中的副本，后续恢复代码（功能模块一的 `RESTORE_ALL`）需要将修改后的值写回 `sepc`，`sret` 才能从新的位置继续执行。

这里的处理目标是跳过实验要求的两类异常指令。假设某条 4 字节非法指令的地址为 `0x1000`，如果处理后 `epc` 仍为 `0x1000`，返回后会再次执行这条指令，可能反复进入异常。将 `epc` 调整为 `0x1004` 后，统一返回流程才能继续执行下一条指令。这个处理策略只针对实验指定的非法指令和断点，不能推广到所有异常：例如缺页异常的处理目标恰恰相反——修复映射后需要**重新执行**出错指令，因此不能推进 `epc`。

#### 关键代码与分支分析

```c
switch (tf->cause) {
case CAUSE_ILLEGAL_INSTRUCTION:
    cprintf("Illegal instruction at 0x%lx\n", tf->epc);
    break;
case CAUSE_BREAKPOINT:
    cprintf("Breakpoint at 0x%lx\n", tf->epc);
    break;
default:
    print_trapframe(tf);
    return;
}

uint16_t instruction = *(const uint16_t *)tf->epc;
tf->epc += (instruction & 3) == 3 ? 4 : 2;
```

`switch` 首先识别异常类型。两个指定分支分别输出异常名称和当前地址，`break` 结束 `switch`，然后共同执行下面的地址更新；输出发生在地址更新之前，所以打印的是触发异常的指令地址。默认分支调用 `print_trapframe(tf)` 输出现场，再用 `return` 结束函数，避免对未知异常读取指令或擅自修改返回地址。打印现场只提供诊断信息，并不表示未知异常已经恢复。

判断指令长度时，`(const uint16_t *)tf->epc` 将保存的地址解释为指向 16 位数据的指针，解引用取得指令的第一个半字。`instruction & 3` 保留最低两位：在本实验的 16 位、32 位指令范围内，最低两位不是 `11` 时将 `epc` 增加 2 字节，是 `11` 时增加 4 字节。例如 `0x9002 & 3` 的结果为 2，因此前进 2 字节；`0x007b & 3` 的结果为 3，因此前进 4 字节。

直接读取 `epc` 所指地址依赖本实验中的内核指令可读取这一前提。若地址不可读取，读取过程本身可能再次触发异常；而 48 位及更长指令也不在当前长度判断的覆盖范围内。这些情况不能因为现有测试通过就认为已经解决。

### 功能模块三：中断处理与时钟中断（组员 B）

**负责人：** 2410625-吴宇轩

#### 模块功能描述

本模块承接练习一保存好的 TrapFrame。处理器把事件原因写入 `scause`，汇编入口将它保存在 `tf->cause`。`trap_dispatch()` 用最高位区分异步中断和同步异常。进入 `interrupt_handler()` 后，仅屏蔽最高位，保留原因编号，再通过 `switch` 分类。时钟中断走调度下一次事件、累计 tick、周期输出、达到次数后关机的路径。其他已定义类型输出诊断提示。未知编号输出原因并调用 `print_trapframe(tf)`。中断分支不修改 `tf->epc`，返回时由练习一的恢复代码及 `sret` 继续原执行流。

#### 关键代码与分支分析

```c
const uintptr_t interrupt_bit = (uintptr_t)1 << (sizeof(uintptr_t) * 8 - 1);
const uintptr_t cause = tf->cause & ~interrupt_bit;
/* switch (cause) 中的时钟分支 */
case IRQ_S_TIMER:
    clock_set_next_event();
    if (++ticks % TICK_NUM == 0) {
        print_ticks();
        if (++reports == SHUTDOWN_AFTER) {
            sbi_shutdown();
        }
    }
    break;
```

`clock_init()` 启用监督级时钟中断，调用 `clock_set_next_event()` 安排首次事件，并把 `ticks` 归零。后者读取 `rdtime`，以当前时间加 `timebase` 计算下一次绝对截止时间，再交给 SBI。该接口设置的是一次性事件，因此处理每次 IRQ 都要重设。按 QEMU 约 10 MHz 时间基准和当前 100000 的增量，名义间隔约 10 ms。处理时间和虚拟机调度会影响实际间隔。

`ticks` 表示累计处理的时钟中断数，每次只增加一次。`reports` 是函数内部静态变量，仅在打印后增加。每累计 100 次调用已有 `print_ticks()` 输出 `100 ticks`，普通运行第 10 次输出后请求 SBI 关机，也就是累计第 1000 次。现有 `DEBUG_GRADE` 条件下 `print_ticks()` 自带提前结束逻辑。其余识别分支只用于分类诊断，没有实现设备中断控制器应答。

| RISC-V 中断与异常机制 | 中断与异常处理 | 本实验中，Trap 是中断和异常的统称。中断一般由时钟或外部设备等异步事件触发，异常则由当前执行的指令触发。操作系统需要根据不同的原因采取对应的处理方式。 |
| RISC-V 特权级与中断委托 | 用户态与内核态、特权级管理 | RISC-V 包含 M、S、U 三种特权级，通过 `mideleg` 和 `medeleg` 可以将部分中断与异常委托给 S 模式处理。本实验主要在 S 模式下处理中断和异常，没有完整实现用户态与内核态之间的切换。 |
| Trap 入口与中断分发 | 中断向量表与中断处理程序 | 本实验通过 `stvec` 设置统一的 Trap 入口 `__alltraps`，再利用 `scause` 判断中断或异常类型，并调用对应的处理函数。相比原理课中介绍的中断向量表，这里采用统一入口后由软件分类处理的方式。 |
| TrapFrame 与上下文管理 | 处理器上下文保存与恢复 | 使用 `struct trapframe` 保存发生 Trap 时的通用寄存器和相关 CSR，使处理程序能够访问原来的 CPU 状态。它体现了操作系统中保存现场、处理事件、恢复现场的基本思想。 |
| `SAVE_ALL` 与 `RESTORE_ALL` | 上下文切换与恢复 | `SAVE_ALL` 将寄存器状态保存到栈上，`RESTORE_ALL` 根据相同的布局恢复状态。两者必须保持对应关系，否则可能造成寄存器数据错误。实际操作系统中的上下文管理还会涉及进程切换等更复杂的情况。 |
| CSR 与 Trap 返回机制 | 处理器状态管理 | `sstatus`、`sepc`、`scause` 等 CSR 分别记录处理器状态、返回地址和 Trap 原因。处理中断或异常时，需要正确维护相关状态，最后通过 `sret` 返回原来的执行流。 |
| 中断与异常分类处理 | 中断处理程序与异常处理程序 | 本实验通过 `trap_dispatch()` 区分中断和异常，再分别调用 `interrupt_handler()` 和 `exception_handler()`。这种分类处理方式与操作系统原理中根据事件类型选择处理程序的思想一致。 |
| 时钟中断处理 | 系统时钟与进程调度 | 本实验利用 OpenSBI 设置时钟事件，通过 `ticks` 记录中断次数，并在每次中断后设置下一次时钟事件。时钟中断也是操作系统实现时间片轮转和抢占式调度的重要基础，但本实验还没有实现真正的进程调度。 |
| 非法指令与断点异常 | 异常检测与处理 | 本实验通过 `scause` 识别非法指令和断点异常，并输出对应信息。处理完成后需要根据指令长度调整 `tf->epc`，避免重复执行已经处理的异常指令。相比之下，缺页异常在完成修复后通常需要重新执行原指令。 |
| 中断使能与临界区保护 | 进程同步、互斥与原子性 | 本实验通过 `intr_enable()`、`intr_disable()` 和 `local_intr_save/restore` 控制中断状态，保护部分内核关键操作。它体现了操作系统中的临界区保护思想，但在多核系统中还需要结合锁等同步机制。 |
| 16 / 32 位混合指令编码 | 变长指令集与对齐 | 压缩指令让指令边界不再固定为 4 字节，任何“按 4 字节步进”的假设（包括异常返回地址调整）都必须先看低两位是否为 `11`。 |
| `satp` 切换与指令提取 | 分页与地址空间切换 | 设置 `satp` 后，取指也要经过地址翻译；切换页表的瞬间必须保证当前指令地址仍有有效映射，否则会因为取指失败而再次陷入。 |

#### 6.2 OS 原理中很重要、但本实验没有对应上的知识点

1. **中断嵌套与优先级**：本实验处理中断期间 `SIE = 0`，不会发生嵌套；真实系统要处理高优先级中断抢占低优先级处理程序、中断栈与嵌套深度限制。
2. **中断下半部 / 软中断 / 工作队列**：实验把所有事情都放在中断上下文里做完（包括 `cprintf`），真实内核会把耗时工作推迟到下半部，避免长时间关中断。
3. **可重入与并发保护**：单核、关中断的前提下没有真正的并发；多核 SMP 下的 per-CPU 数据结构、IPI（核间中断）与锁竞争完全未涉及。
4. **外部中断控制器（PLIC）**：实验只用到 S 态时钟中断（`IRQ_S_TIMER`），没有设备中断的申请、使能、优先级与应答流程。
5. **用户态与特权级切换**：本实验所有 Trap 都发生在内核态，`SPP` 恒为 1；U→S 的栈切换（`sscratch` 交换）、系统调用（`ecall`）路径未覆盖。
6. **缺页异常与按需分页**：`CAUSE_FAULT_LOAD/STORE` 在本实验里只是 `print_trapframe` 兜底输出，没有真正的页面置换、写时复制。
7. **抢占式调度**：时钟中断只做计数和打印，没有触发调度器；"中断返回时选择下一个进程"这一关键衔接没有出现。
8. **异常的语义化处理**：真实系统会把异常翻译成信号（如 `SIGSEGV`、`SIGILL`）交给进程，本实验只是打印并跳过。
9. **用户态地址的安全读取**：异常处理直接解引用 `tf->epc` 读取指令半字，前提是该地址在内核可读范围内；真实内核读取用户指针必须做合法性校验，否则可能引发二次异常或泄露内核数据，本实验未涉及。
10. **超长指令与多套指令集**：指令长度判断只覆盖 16 / 32 位，48 位及以上编码不在范围内。

### AI 协作开发的经验

1. 提示词要尽量具体、清楚。 一开始如果只是简单告诉 AI 要实现哪个函数，生成的代码可能会遗漏一些关键细节。后来我们按照 [PROMPT]、[RELY]、[GUARANTEE] 和 [SPECIFICATION] 四部分组织提示词，把已有接口、功能要求和限制条件说明清楚，生成的代码也更符合实验要求。

2. 不能完全依赖 AI 生成的代码。 在实现 Trap 上下文恢复时，我们发现寄存器的恢复顺序非常重要。例如，过早修改 sp 就可能导致后续寄存器读取错误。因此，即使 AI 已经生成代码，也需要结合实验指导书和已有代码逐步检查，理解每段代码的实际作用。

3. 遇到问题要结合工具进行分析。 在测试过程中，我们曾遇到寄存器检查失败的情况。开始以为是上下文恢复代码有问题，后来通过查看 TrapFrame 和使用 objdump 分析反汇编，发现是临时异常处理函数没有正确考虑指令长度。这让我们认识到，不能只根据报错信息判断问题，还需要结合实际运行结果逐步排查。

4. AI 更适合作为辅助工具，而不是直接代替思考。 这次实验中，AI 帮助我们理解了一些比较复杂的汇编指令和中断处理流程，提高了代码编写和问题排查的效率。但最终还是需要自己检查代码、进行测试，并根据实际情况调整实现方式。

5. 给出数据结构、允许修改的范围和返回条件，比只说“完成异常处理”更容易得到可检查的实现。 异常处理的提示词里明确写出了 `struct trapframe` 的字段、`trap_dispatch()` 已经做过分发、只能改 `exception_handler()`，并把“指令长度判断”的规则和边界（16/32 位、地址可读）写在前置条件里，因此生成的代码在复核时基本可用。

6. 测试需要区分“函数逻辑检查”与“系统运行验证”。 异常处理的脚本是用构造的 Trap frame 调函数，它能覆盖分支与地址计算，但没有经历“硬件压栈 → 汇编保存 → C 处理 → 汇编恢复 → `sret`”这条真实路径；因此报告里必须写“逻辑检查通过，不代表真实 Trap 返回已验证”，不能混为一谈。
