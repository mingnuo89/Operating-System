## 一、实验目的

<!-- 说明本次实验的主要目标和预期成果 -->

本实验的主要目的是：

1. 理解操作系统内核**无法依赖宿主操作系统的运行时库**，必须自底向上构建自身的输入输出能力；
2. 掌握 RISC-V 下**跨特权级服务调用**的机制：为什么需要 `ecall`、如何用内联汇编实现 SBI 的调用约定、如何在此基础上层层封装出 `cprintf`；

4. 学习使用 AI 辅助开发操作系统核心功能，并按规范记录提示词与迭代过程。

## 三、实验整体逻辑分析

### 2.1 本章节的逻辑主线

本章实验围绕一个核心主题展开：**如何让一个"一无所有"的内核在裸机上运行起来，并说出第一句话**。

在没有操作系统、没有任何运行时库的前提下，内核必须自己解决三个问题：**在哪里运行**、**如何与外界通信**、**如何从源码变成能运行的东西**。这三者对应 lab1 的三个功能模块：

1. **内核的内存布局和入口点设置**——解决"内核在哪里运行、从哪里开始运行"；
2. **通过 OpenSBI 封装输入输出函数**——解决"内核如何与外界通信"；
3. **构建流程（Makefile）**——解决"如何把代码变成能在 QEMU 上运行的镜像"。


### 2.2 功能的逐步实现

本章功能按照"**先能加载、再能说话、最后能自动化**"的顺序逐步实现。以下先给出总体顺序，随后**只展开本人负责的两项**；其余各项由同组其他成员撰写，此处留空。

**总体顺序：**

1. 首先确定内核的**内存布局与入口点** → 为什么首先实现这个？〔由同组另一位成员撰写，此处留空〕
2. 接着构建**输入输出能力** → 为什么接着实现这个？
3. 然后建立**自动化的构建流程** → 为什么最后实现这个？

**以下为本人负责的两项：**

2. **接着构建输入输出能力** → 为什么接着实现这个？

   内核入口 `entry.S` 只做两件事：初始化内核栈、跳转到 C 函数 `kern_init`。而 `kern_init` 需要调用 `cprintf` 输出启动信息，以证明内核确实开始运行。但内核自身尚未成型时**无法依赖任何现成的运行时库**（否则构成"开发操作系统却依赖另一个操作系统"的循环依赖），因此必须从硬件提供的最原始接口出发，自底向上构建输出能力。这是本人负责的第 2 项。

3. **最后建立自动化的构建流程** → 为什么最后实现这个？

   前三步涉及"编译所有源码 → 链接成 ELF → 生成 BIN 镜像 → 用 QEMU 加载运行"一长串命令，手敲一次容易出错、也难以复现和增量更新。因此需要 Makefile 把这条流水线固化下来，通过**依赖关系**驱动构建，借助时间戳比较实现**增量编译**。这是本人负责的第 3 项。

**整个 lab1 的成品**：执行 `make qemu` 后，终端先输出 OpenSBI 固件的启动横幅，随后出现一行

```
(THU.CST) os is loading ...
```

该行由 `kern_init` 中的 `cprintf` 打印，**它的出现同时证明了构建链、加载流程与输出能力三者全部打通**——这正是本章三个功能模块共同的成果。

### 功能模块：从 SBI 到 stdio

**负责人：** 2410878-吕明诺

#### 模块功能描述

**需要实现/修改的函数：**

本模块在框架中已完整实现，涉及理解与验证的函数签名如下：

```c
/* libs/sbi.c —— SBI 调用封装 */
uint64_t sbi_call(uint64_t sbi_type, uint64_t arg0, uint64_t arg1, uint64_t arg2);
void sbi_console_putchar(unsigned char ch);
void sbi_set_timer(unsigned long long stime_value);

/* kern/driver/console.c —— 控制台驱动，类型适配层 */
void cons_putc(int c);
int  cons_getc(void);

/* kern/libs/stdio.c —— 高层输入输出 */
static void cputch(int c, int *cnt);
void cputchar(int c);
int  cputs(const char *str);
int  vcprintf(const char *fmt, va_list ap);
int  cprintf(const char *fmt, ...);
int  getchar(void);

/* libs/printfmt.c —— 格式化引擎 */
void vprintfmt(void (*putch)(int, void *), void *putdat, const char *fmt, va_list ap);
int  snprintf(char *str, size_t size, const char *fmt, ...);
```

**功能说明：**

该模块位于**内核与硬件固件之间**，作用是为内核提供**格式化输出能力**，使内核能够向开发者/用户输出运行信息。

需要处理的主要场景：

- 内核运行在 **S 模式（Supervisor）**，而提供服务的 OpenSBI 固件运行在 **M 模式（Machine）**，二者之间存在特权级壁垒，**无法使用普通函数调用跨越**；
- C 语言本身**无法直接表达 `ecall` 指令**，也**无法指定变量占用哪个物理寄存器**，而 SBI 调用约定要求参数必须位于固定寄存器，因此必须借助**内联汇编**完成寄存器级的参数传递；
- 从"输出一个字符"这一唯一能力出发，需要逐层抽象，最终提供与标准库 `printf` 语义相当的接口。

与其他模块的交互关系：

- **向下**依赖 OpenSBI 固件提供的 `SBI_CONSOLE_PUTCHAR`（功能号 1）服务；
- **向上**为 `kern/init/init.c` 提供 `cprintf`，使 `kern_init` 能输出启动信息；
- 与"内存布局与入口点"模块的交汇点是 `init.c` 中的 `memset(edata, 0, end - edata)`——该语句用到的 `edata` 与 `end` 正是链接脚本 `kernel.ld` 通过 `PROVIDE` 定义的符号。

### 功能模块：Just make it

**负责人：** 2410878-吕明诺

#### 模块功能描述

**需要实现/修改的函数：**

本模块不涉及 C 函数，涉及的是构建脚本中的目标与宏：

```make
# Makefile 中的关键目标
qemu:            # 启动 QEMU 运行内核
debug:           # 启动 QEMU 并等待 GDB 连接（-s -S）
gdb:             # 启动 GDB 连接 QEMU
grade:           # 运行评分脚本
clean:           # 清理构建产物
dist-clean:      # 彻底清理
tags:            # 生成 cscope/ctags 索引

# tools/function.mk 中定义的关键宏函数
listf / toobj / todep / totarget / packetname
add_files / create_target / read_packet / finish_all
```

**功能说明：**

该模块是项目的**构建系统**，作用是把 `kern/`、`libs/` 目录下的所有 C 与汇编源码自动地编译、链接、转换，最终生成可被 QEMU 加载的内核镜像。

需要处理的主要场景：

- 源码分布在多个目录，需要**自动收集**而非手工罗列文件清单；
- 需要**增量编译**，只重建被修改过的文件及其依赖；
- 需要处理"源码 → 目标文件 → ELF → BIN 镜像"的**多阶段转换**；
- 启动 QEMU 时必须把内核加载到 **`0x80200000`**，与 OpenSBI 的约定保持一致。

与其他模块的交互关系：

- 依赖 `tools/function.mk` 提供的宏函数完成文件收集与目标生成；
- 依赖 `tools/kernel.ld` 完成链接阶段的地址与段布局指定；
- **最终产物 `bin/ucore.img` 是"从 SBI 到 stdio"模块能否被验证的前提**——没有镜像就无法运行，也就看不到任何输出。

## 六、实验总结与收获

### 对操作系统的理解

#### 1. 本实验中的重要知识点，以及与对应 OS 原理中知识点的关系

| 本实验中的知识点 | 对应 OS 原理中的知识点 | 二者的含义、关系与差异 |
|---|---|---|
| `ecall` 指令：在 S 模式执行时陷入 M 模式，调用 OpenSBI 服务 | 系统调用机制（用户态执行 `ecall` 陷入内核态） | **含义**：两者都是通过 `ecall` 实现"受控的权限提升"，由低特权级主动请求高特权级提供服务。**关系**：本实验的 SBI 调用是系统调用机制在"内核 → 固件"这一层的同构实现，调用约定（功能号放 `a7`、参数放 `a0`–`a2`、返回值取 `a0`）完全一致。**差异**：系统调用的目标是被开发的操作系统内核，处理文件、进程、内存等资源管理；SBI 调用的目标是固件，提供控制台 I/O、设置定时器等硬件相关基础服务。本实验可视为理解系统调用的"预演"。 |
| `sbi_call` 用内联汇编固定寄存器分配 | C 语言与硬件的接口设计 / ABI（应用二进制接口） | **含义**：C 语言不保证变量占用哪个寄存器，而跨特权级调用要求参数必须位于约定的寄存器。**关系**：ABI 是编译器、汇编代码与硬件之间的契约；内联汇编是在 C 中"手工满足该契约"的手段。**差异**：普通函数调用的寄存器分配由编译器自动完成；跨特权级调用必须由程序员显式指定。 |
| 从"输出一个字符"逐层封装到 `cprintf` | 抽象层次划分 / 层次化设计 | **含义**：把复杂功能分解为多层接口，每层只解决一个问题。**关系**：操作系统整体结构（硬件抽象层 → 内核 → 系统调用接口 → 用户库）正是这种分层思想的宏观体现。**差异**：本实验的分层是**同一特权级内**的函数封装；OS 的分层通常**跨特权级**，还涉及保护边界的建立。 |
| `vprintfmt` 通过函数指针回调输出 | 接口与实现分离 / 多态思想 | **含义**：格式化引擎不关心字符最终输出到何处。**关系**：这是"依赖倒置"的具体应用，与 OS 中设备驱动接口、文件系统操作表的设计思想一致。**差异**：本实验只是一个函数指针参数；OS 中通常是一整张操作表，支持运行时动态替换。 |
| Makefile 的依赖驱动构建与增量编译 | 程序的编译、链接与装入 | **含义**：make 依据"目标是否比依赖旧"决定是否重建。**关系**：链接脚本规定各段的布局，对应 OS 原理中"装入"阶段确定程序内存映像的过程。**差异**：普通应用程序由操作系统装入并重定位，可采用动态链接与地址无关代码；本实验的内核是**地址相关**的，必须装入固定的物理地址 `0x80200000`，装入工作由 QEMU 完成。 |
| `.bss` 段在镜像中不存数据，需运行时清零 | 程序的内存映像（`.text`/`.data`/`.bss` 布局）、进程地址空间 | **含义**：`.bss` 只记录大小与位置，加载后需由程序自行清零。**关系**：`kern_init` 中的 `memset(edata, 0, end - edata)` 与操作系统为进程初始化 `.bss` 段是同一件事。**差异**：本实验中由内核自己完成（因为尚无进程概念）；在完整 OS 中，这属于**程序装入器**的职责。 |
| 链接脚本中的 `PROVIDE(edata = .)` / `PROVIDE(end = .)` 符号 | 链接与符号解析 | **含义**：`PROVIDE` 定义的符号只在被引用时才生成，其值为当前位置的地址。**关系**：与 C 语言变量不同，它们是**链接器符号**，只有地址、没有存储空间。**差异**：C 变量有类型和存储；链接器符号无类型，其"值"就是地址本身。 |
| ELF 与 BIN 格式的差异及 `objcopy` 转换 | 可执行文件格式与程序装入 | **含义**：ELF 含文件头、调试信息与段布局描述；BIN 是可直接放入内存的线性映像。**关系**：两者是同一程序的不同表示形式，`objcopy` 完成转换。**差异**：ELF 需要装入器解析后才能运行；BIN 可直接被放到约定地址执行，因而适合资源受限的固件（OpenSBI）加载。 |

#### 2. OS 原理中很重要、但在本实验中没有对应上的知识点

1. **进程与线程管理**。本实验的内核只有单一执行流，`kern_init` 打印一行后即进入死循环，没有进程控制块、没有调度器、没有上下文切换，因此不存在"进程"这一抽象。
2. **虚拟内存与地址翻译**。本实验全程使用**物理地址**（`0x80200000` 直接被装入并执行），尚未建立页表、未开启分页机制，因此没有虚拟地址到物理地址的转换，也没有缺页异常处理。
3. **文件系统**。本实验没有磁盘 I/O、没有 inode、没有目录结构；构建产物通过 QEMU 的 `-device loader` 直接加载，不经过任何文件系统。
4. **进程间通信与同步**。由于不存在多执行流，信号量、互斥锁、条件变量等同步机制在本实验中均无对应。
5. **用户态与保护机制**。虽然真实 RISC-V 系统中还存在 U 模式，但本实验没有任何用户程序，因此没有 U/S 特权级切换（`ecall` 只被用作 S→M 的服务请求），也没有地址空间的隔离与保护。
6. **中断与异常处理的完整机制**。本实验仅用到 `ecall` 这一种陷入方式，尚未建立中断向量表、未处理时钟中断、没有中断嵌套与中断屏蔽机制。
7. **设备驱动模型**。本实验只通过 SBI 间接使用控制台，没有直接操作设备寄存器，也没有统一的驱动接口与设备抽象层。
8. **死锁与资源分配**。没有并发与资源竞争，因此死锁的四个必要条件在本实验中无从体现。

### AI 协作开发的经验

1. **"说清楚"比"说得多"更重要。** 最初用"帮我讲讲从 SBI 到 stdio 这条链"这类模糊提问，得到的是泛泛而谈；改为明确列出文件路径、给出已知的系统约束（S 模式 / M 模式）、要求引用真实函数签名之后，回答才具备可核对的准确性。这与实验讲义强调的"说清楚比说简洁更重要"是一致的。

2. **必须防止 AI 对不存在的代码产生幻觉。** 本实验所用的代码包存在文件缺失（如 `kern/trap/`、`kern/driver/clock.c` 均不存在）。若不明确要求"若函数不存在必须指出、不得臆测"，AI 很可能会依据 uCore 的通行版本"补全"出一份并不存在于本工程中的代码。**这是本次实验中最重要的一条经验。**

3. **要让 AI 区分"讲义写法"与"真实代码写法"。** `kernel.ld` 的差异就是这样被发现的：讲义把 `*(.text.kern_entry)` 单独列一行，实际代码则合并成了一行。若不加这条约束，很容易把讲义内容当作代码事实写进报告。

4. **AI 生成的解释必须用实测验证。** 例如"完整调用链已打通"这一结论，最终是通过 `make qemu` 实际输出 `(THU.CST) os is loading ...` 得到印证的。**代码能否跑起来，是检验理解是否正确的最终标准。**

5. **工具性手段往往比静态阅读更高效。** 面对 `tools/function.mk` 中复杂的 `$(eval ...)` 宏，直接阅读相当困难；执行 `make -n qemu` 打印展开后的命令序列则一目了然。遇到难以静态理解的构建系统，应当优先用工具观察其行为。

6. **AI 适合承担"梳理与核对"，不适合承担"判断与决策"。** 调用链的整理、选项含义的查询、讲义与代码的逐条比对，AI 效率很高；但"这个设计是否合理""两种写法是否等价"这类判断，仍需结合实测结果由开发者自行确认。**最终的负责人始终是开发者本人。**
